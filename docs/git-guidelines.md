# Git 使用规范

本文档约束本仓库的 Git 提交说明与提交操作。人工提交和自动化提交均应遵守。

## 一、提交说明格式

### 1. 使用中文结果描述

提交标题直接说明本次提交完成的能力或解决的问题，采用“动作 + 对象 + 结果”的写法。

推荐使用以下动词开头：

- `建立`：形成新的机制、边界或闭环
- `实现`：完成一项完整能力
- `接入`：连接外部服务、接口或内部链路
- `完善`：补齐已有能力
- `修复`：解决明确缺陷
- `统一`：收敛重复实现或不一致行为
- `补充`：增加必要但相对独立的内容

技术名词可以保留英文，例如 `API`、`SQLite`、`Collector`、`Local/Global`。

### 2. 禁止 Conventional Commits 前缀

提交标题禁止以 `feat`、`fix` 等类型前缀开头，也不使用带作用域的形式。

禁止示例：

```text
feat(backend): 新增店铺能力
fix(config): 修复环境加载问题
refactor: 调整商品服务
chore(docs): 更新文档
```

正确示例：

```text
实现 Local/Global 单链路商品草稿与刊登编排
接入受保护的商品与订单核心 API
建立 Collector 来源注册与受控出站边界
建立安全增值工具与 SQLite 调度闭环
建立刊登模式证据持久化与人工确认闭环
```

### 3. 标题要求

- 标题应简洁、完整，能够独立表达提交目的。
- 一个提交只描述一个主要目标，避免使用“若干修改”“更新代码”等模糊表述。
- 标题末尾不加句号。
- 不得提交包含 `??`、乱码、不可识别字符或错误编码的说明。
- 正文仅在需要解释背景、约束或重要取舍时添加，不重复标题内容。

## 二、提交操作要求

### 1. 提交前检查

提交前必须确认：

1. 当前分支和工作区状态。
2. 已暂存与未暂存的差异。
3. 本次提交包含的文件和改动范围。
4. 提交标题符合本规范，并与仓库早期提交风格一致。

不得为了方便直接把无关改动加入同一个提交。工作区存在其他未提交内容时，只暂存当前任务涉及的文件。

### 2. 提交后验证

提交完成后必须检查最新提交说明和工作区状态，确认：

- 中文显示正常，没有乱码。
- 提交内容没有夹带无关文件。
- 原有未提交改动仍然保留。
- 分支与远端的领先或落后关系符合预期。

可使用以下命令检查：

```bash
git log -1 --format="%H%n%s%n%n%b"
git status --short --branch
```

### 3. 修改最后一次提交说明

仅修改尚未推送的最后一次提交说明时，使用：

```bash
git commit --amend --only -m "新的中文提交说明"
```

`--only` 用于避免把当前暂存区中的其他改动带入修订后的提交。执行后必须再次检查最新提交和工作区状态。

如果提交已经推送，修改说明会重写提交历史并产生新的提交哈希。未经明确确认，不得修改已推送提交，也不得执行强制推送。

## 三、安全要求

- 未经明确要求，不执行 `git push`。
- 未经明确要求，不执行 `git commit --amend`。
- 不使用 `git reset --hard`、`git checkout --` 等命令丢弃现有改动。
- 不回退或覆盖来源不明、与当前任务无关的工作区改动。
- 不跳过提交钩子，除非已有明确授权并说明原因。
- 中文提交说明必须使用 UTF-8，并在提交后立即检查显示结果。
